# A deck's past is git's, a snapshot is a tag, and a variant is another deck

Every save is already a commit, and its message is the deck's changelog ([ADR-0021](0021-curator-owns-one-fixed-name-repo-and-saves-by-itself.md)). So Meldweb Curator keeps no history of its own. It reads git's, and it adds to it only through the saves it already makes.

- **A deck's history is the commits that touched its path** on the default branch, newest first (`GET /commits?path=`). The path never moves, so the list is complete. A **revision** is the file as one of those commits left it, read with the Contents API at `?ref=<commit>`. "How did it look on the 28th" is the newest commit at or before that day (`?until=`).
- **A revision is a link.** `/deck/<path>?at=<commit>` shows the deck as that commit left it, in place of its stacks, beside the deck as it is now. `?vs=<path>` does the same with another deck. The editor stays mounted underneath and keeps saving.
- **What differs is `chip-decklist`'s diff**, the one that writes commit messages. Each difference is a change the deck as it is now could **take**: a card back, a card out, a quantity, a category, the description. Taking applies the chosen changes to the deck's text with the same edits as the rest of the editor. It leaves comments, spacing and every other line as they were, and the result must parse. That makes it an ordinary edit: it saves by itself, and Ctrl+Z undoes it. **Restoring** a revision is taking every change, so it is one new commit on top and never a rewrite.
- **A snapshot is an annotated tag** named `decks/<stem>/<slug>`, whose message is the label the user typed ("FNM 14 Sep") and whose tagger date is when it was taken. The prefix makes each deck list only its own (`git/matching-refs/tags/decks/<stem>/`). The tag is annotated, not lightweight, because it needs both the label and the date. Creating and listing tags is Contents permission, which the app already has.
- **A variant is a deck file of its own**, with `variant_of = "<parent path>"` among its metadata, beside `name` and `format`. It starts as any revision of the parent, the current one or one from history. Its page compares it with its parent, and the parent's page lists its variants. Either one can take the other's changes, and that is how a variant merges back. Between two decks, the variant's `name` and `variant_of` are never taken, since those make it a different deck. Gauntlet does not read `variant_of`, and a parent that is gone leaves the variant as an ordinary deck.

## Considered Options

- **Variants as git branches.** Rejected. A branch forks the whole repo, `collection.toml` included, and a copy of a card is in one place ([ADR-0023](0023-the-collection-is-one-file-and-a-copy-is-in-one-place.md)). Two branches would be two records of where the same physical Sol Ring is. Curator reads and saves the default branch only, so a deck on a branch would vanish from the deck list, from the collection's deck places and from every other page. Two decks in one tree keep each save to one file and one commit.
- **Restore as `git revert`, or by moving the branch back.** Rejected. A revert undoes one commit, not "go back to the 28th", and moving the branch rewrites history the user can see on GitHub. Taking every change is an ordinary save that undoes like any other edit.
- **A line diff of the TOML.** Rejected as what the user reads and takes. It shows a moved card as a removed and an added line, and taking half of one leaves a file that may not parse. The semantic diff is already the commit message, so the comparison and the changelog say the same thing.
- **Lightweight tags for snapshots.** Rejected. They carry no label or date, so a snapshot would be named only by its slug and dated by its commit.
- **Snapshots or history kept in the repo as files.** Rejected. Git already keeps both, and a second copy could disagree with it.
