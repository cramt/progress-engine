# gitaxian-probe-app

The Dioxus Native (Blitz) shell for Gitaxian Probe, cross-compiling to an Android
APK from NixOS. No WebView — Blitz lays out the HTML/CSS and Skia paints it
straight to a Surface.

**It is still the hello world.** Nothing here talks to `gitaxian-probe-engine`
yet; what this crate establishes is that the toolchain works, and the notes below
are the parts of that which were expensive to find out.

## Run it

```sh
# desktop, to check the UI without a phone - the default shell is enough
nix develop
cargo run -p gitaxian-probe-app

# phone over USB (adb debugging on). The Android SDK is unfree and about a
# gigabyte, so it lives in a shell of its own rather than the default one.
nix develop .#android
cd crates/gitaxian-probe/app
dx serve --android --renderer native --target aarch64-linux-android
```

`dx` reads `Dioxus.toml` and `MainActivity.kt.hbs` from the crate directory, which
is why the Android command runs from in here rather than the workspace root.

`default = ["skia"]` in `Cargo.toml` picks the renderer, so neither command needs
extra feature flags.

**`--renderer native` is not optional.** In dx 0.8.0-alpha.1 `--android` is an alias
for `--target <triple> --renderer webview --bundle-format android`, so a bare
`dx serve --android` silently builds a *WebView* app. There is no `--native`
shorthand yet — the `RendererArg` import is still commented out in the CLI source,
even though `--target`'s help text advertises the flag.

## Why the versions are what they are

**Dioxus 0.8.0-alpha.1, not 0.7.10.** `dioxus-native` 0.7 hardcodes `anyrender_vello`
with no way to swap it, and Vello renders [a black screen on
Android](https://github.com/DioxusLabs/blitz/issues/377). The `skia` / `vello` /
`vello-hybrid` / `vello-cpu` feature flags only exist from 0.8.0-alpha.1 on.

**Skia, not Vello.** From that same issue, confirmed by a Blitz maintainer: Vello is
black-screen, `vello-hybrid` "works but stutters, lot of quirks", Skia is reliable.
The one-line summary was *"just use skia on mobile"*. Swap to `--features vello-hybrid`
in a year or so when it has matured.

**`dx` is overridden in the workspace `flake.nix`.** nixpkgs ships 0.7.10, and dx refuses to drive a
workspace whose `dioxus` version it doesn't match. The override inherits nixpkgs'
`no-downloads` build feature, which is the bit that stops dx fetching its own
toolchains at runtime — the thing that would otherwise break on NixOS.

## If you'd rather have the WebView

The Android shell in the workspace `flake.nix` is renderer-agnostic — the NDK, the aapt2 override, the linker
env vars, the rust targets and the JDK are all exactly what a WebView build needs
too. So the hard part carries over unchanged.

The *app* is not a one-flag switch, though, because this one calls
`dioxus_native::launch` directly. A WebView port means:

- `dioxus = { version = "0.8.0-alpha.1", features = ["mobile"] }` instead of the
  `dioxus-native` dependency, and `dioxus::launch(app)` in place of
  `dioxus_native::launch(app)`
- dropping `android_main_activity` from `Dioxus.toml`, since the stock template
  already subclasses the WebView activity
- dropping the `skia` / renderer features entirely

`src/app.rs` itself ports across untouched — it's the same rsx and the same CSS.
The trade is real WebView consistency problems (and a much bigger APK) against
Blitz's missing safe-area insets and touch events.

## The NixOS-specific bits

These are the parts that are annoying to rediscover:

- **`android_sdk.accept_license` + `allowUnfree`** in the nixpkgs config, or
  `composeAndroidPackages` refuses to evaluate. The workspace flake imports
  nixpkgs a second time as `androidPkgs` to get them, so the unfree licence does
  not follow the default shell around.
- **aapt2.** Gradle downloads its own prebuilt aapt2, whose ELF interpreter path
  doesn't exist on NixOS. `GRADLE_OPTS` points it at the patched one from
  `build-tools` instead.
- **`ANDROID_NDK`.** rust-skia's build script reads this exact variable — not
  `ANDROID_NDK_ROOT` or `ANDROID_NDK_HOME`, which everything else uses. All three
  are set.
- **`python3`.** Stylo generates Rust source from Python at build time. Blitz's own
  flake carries this too; without it the build dies deep inside a build script.
- **Per-target linker vars.** `CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER` plus
  `CC_`/`CXX_`/`AR_`/`RANLIB_` for the cc-rs crates. Generated by `androidCrossEnv` in
  the flake so adding an ABI is a one-line change, and kept in env vars rather than
  a committed `.cargo/config.toml` so no nix store paths get checked in.

## Safe-area insets

Blitz doesn't resolve `env(safe-area-inset-*)` on Android yet — [blitz#370](https://github.com/DioxusLabs/blitz/pull/370)
is the draft, blocked on [winit#4506](https://github.com/rust-windowing/winit/pull/4506).
Until it lands, `SAFE_TOP_PX` / `SAFE_BOTTOM_PX` in `src/app.rs` are hardcoded.
Tune them once for your phone; the two tinted bars in the UI exist to make it
obvious when they're wrong.

## Known rough edges

In this build:

- **The manifest under-declares minSdk.** `android_min_sdk_version = 26` only steers
  which NDK clang wrapper dx links against; dx's generated `app/build.gradle.kts`
  hardcodes `minSdk = 24` and there is no config key for it. The APK therefore
  claims to support API 24 while the native code needs 26 — on a genuine API 24/25
  device it would install and then crash on `dlopen`. Irrelevant on any phone from
  the last several years; worth knowing before you hand the APK to someone else.
- **`--target` is required.** With no device attached dx assumes an emulator and
  picks `x86_64-linux-android`.
- Debug APK is ~105 MB, most of it unstripped Skia. `--release` (with the `strip`
  and `lto` settings already in `Cargo.toml`) cuts that down hard.

Inherited from Dioxus Native on Android generally, not from this setup:

- No safe-area insets (above).
- Pointer events only — no raw touch events, so no multi-touch or custom gestures.
  Drag-to-scroll and momentum scrolling do work.

## What was actually verified

Built, installed and run on a OnePlus CPH2719 (Android 16, API 36, arm64-v8a):
the app launches, paints its gradient full-screen, and counts taps. Frames reach
the compositor (`BufferQueueProducer ... queueBuffer: fps=8.58`) with no
`AndroidRuntime` or native-crash entries in logcat.

That it is genuinely not a WebView, if you ever doubt the subtitle:

- zero `wry` / `tao` / `webkit2gtk` / `dioxus-desktop` entries in `Cargo.lock`
- `MainActivity` subclasses `android.app.NativeActivity`
- `lib/arm64-v8a/libmain.so` exports `android_main` and `ANativeActivity_onCreate`
  and carries ~7000 Skia symbols
- `cargo tree --target aarch64-linux-android` shows `anyrender_skia` and zero
  occurrences of `anyrender_vello`

The `SAFE_TOP_PX` / `SAFE_BOTTOM_PX` defaults were checked on that same phone —
the bars clear the status bar and the gesture pill.

### What the move re-checked, and what it did not

The phone run above is from before this crate joined the monorepo, and the
Android path has not been re-run since: the package was renamed, the crate
moved two directories deep, and the SDK/NDK shell was rebuilt as
`devShells.android` in the workspace flake. None of that should change what dx
produces, but "should" is not the same as watched.

Re-checked here: the desktop build and run (`cargo run -p gitaxian-probe-app`
paints its gradient and counts taps), that the binary links with nothing
missing, that the Android rust-std for both triples comes from the toolchain
file, and that both shells evaluate. Point a phone at it before trusting the
APK half again.
